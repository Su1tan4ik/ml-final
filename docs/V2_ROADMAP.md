## Зачем V2

V1 считает пробку как среднее по тайлу (z14/z15, ~0.9–1.8 км): магистраль красная,
дворы зелёные → тайл «жёлтый». Цель V2:
1. Показывать пробки **по дорогам** (линии по улицам, как в Яндекс/2GIS), включая мелкие улицы.
2. Прогнозировать загруженность **каждого участка дороги**.
3. В будущем — **маршрут A → B в обход пробок** (с учётом прогноза).

## Ключевая идея: тайл ≠ единица измерения

Пиксели трафика в тайле Яндекса **нарисованы вдоль дорог**. Если знать, какой пиксель
лежит на какой OSM-дороге (map-matching), то score считается **на отрезок дороги**, и размер
тайла влияет только на разрешение (м/пиксель), а не на усреднение.

| Зум | Тайлов на bbox | Тайл | м/пиксель |
|---|---|---|---|
| 15 | 648 | ~890 м | 3.5 |
| 16 | 2 491 | ~445 м | 1.7 |
| 17 | 9 752 | ~220 м | 0.9 |
| 18 | 38 613 | ~110 м | 0.4 |

**Вывод по «220 м не много ли?»:** при привязке пикселей к дорогам размер тайла не важен
для детализации. Важно (а) разрешение, чтобы соседние параллельные дороги не сливались, и
(б) на каком зуме Яндекс вообще рисует трафик на мелких улицах. Это проверяем экспериментом
(этап 1.1). Ожидание: z16 — хороший компромисс (4× меньше запросов, чем z17).

## Целевая архитектура

```
[cron на сервере, каждые 10–30 мин]
  scraper: качает тайлы Яндекса (только тайлы, где есть дороги)
    → numpy: маска цветов по пикселям
    → pixel→road lookup (предрасчитан) → score на road_segment
    → PostgreSQL: traffic_obs(ts, segment_id, score, n_pixels, ...)
  weather → PostgreSQL: weather_obs(ts, ...)

[cron раз в сутки]
  features (SQL/pandas, векторно) → train (XGBoost) → models/ + метрики
  model gate: хуже прошлой или хуже naive → не деплоить

[FastAPI + MapLibre GL, docker compose, на сервере]
  /api/traffic/now        — текущие скоры по сегментам (GeoJSON / vector tiles)
  /api/traffic/forecast   — прогноз на +30/+60 мин
  /api/route?from&to&t    — маршрут A→B (pgRouting, вес = время с учётом пробок)
```

### Схема БД (черновик)

- `road_segment(id, osm_way_id, name, highway, oneway, lanes, maxspeed, length_m, geom LINESTRING, source, target)` — ребро графа (way, разрезанный по перекрёсткам)
- `road_node(id, osm_node_id, geom POINT)` — вершины графа
- `tile_pixel_map(z, x, y, px, py, segment_id)` — или сжатый вариант: для каждого тайла список (segment_id, индексы пикселей)
- `traffic_obs(ts, segment_id, score, n_pixels, pct_free, pct_slow, pct_moderate, pct_heavy)` — партиционировать по месяцу
- `weather_obs(ts, temp_c, humidity, wind_ms, precip_1h, visibility_m, condition)`
- `forecast(ts_made, ts_target, segment_id, score_pred)`

## Маршрутизация A → B (будущее)

- Граф: вершины = перекрёстки OSM, рёбра = участки дорог (учитывать `oneway`).
- Вес ребра = время проезда: `length_m / speed(score)`, где `speed` из текущего или прогнозного score
  (если по ребру нет данных — `maxspeed` / скорость по типу дороги).
- Алгоритмы:
  - **Dijkstra / A\*** (A* с эвристикой = расстояние / макс. скорость) — для MVP, через **pgRouting** (`pgr_aStar`, `pgr_dijkstra`) прямо в PostgreSQL.
  - **Time-dependent A\***: вес ребра зависит от времени прибытия на ребро (используем прогноз +30/+60 мин) — это и есть «маршрут в обход будущей пробки».
  - Если не хватит скорости: OSRM / Valhalla / GraphHopper с кастомными весами (Contraction Hierarchies).
- Сравнивать: маршрут «кратчайший» vs «быстрейший с учётом пробок», выигрыш в минутах.

## Риски / открытые вопросы

- **Блокировка Яндексом** при 2.5–10 тыс. запросов на прогон. Нужны паузы, ограничение параллельности, кеш, возможно меньшая частота ночью. Правовую сторону использования тайлов Яндекса тоже стоит учесть.
- Рисует ли Яндекс трафик на `residential`/`service` вообще? Если нет — для мелких улиц прогноз только по соседям/типу дороги.
- Объём: ~30–50 тыс. сегментов × 48 прогонов/сутки ≈ 1.5–2.5 млн строк/сутки → партиционирование, хранить только сегменты с пикселями.
- Привязка пикселей на развязках/параллельных дорогах (одна линия пикселей рядом с двумя дорогами).
